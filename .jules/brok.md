# Brok's Journal
## 2026-10-02 - Code Coverage and Type Error Edge Cases in Python Engine
**Learning:** PyArrow RecordBatches strictly enforce underlying memory types. Passing `np.int32` arrays down to the Rust engine expecting `Float32Array` correctly throws an error, but this error handling path (`TypeError` gracefully propagated up) wasn't explicitly tested. Similarly, the engine safely returns zero arrays for zero-length `RecordBatch` inputs, but the Python bindings had gaps for edge case validation.
**Action:** Adding explicit tests for type conversion errors (`TypeError` for non-float32 columns) and empty batch inputs makes the system demonstrably more robust, assuring developers that failures will be graceful exceptions rather than Rust panics at the FFI boundary.
## 2026-10-05 - Consistent Exception Boundaries across Extractor Classes
**Learning:** In the `tsfast` codebase, the Rust-Python FFI boundary throws a `ValueError` with "Unknown feature" when initialized with an unparseable feature string. While this edge case was covered for the static `Extractor` and `SlidingExtractor`, it was missing for `ExpandingExtractor`. Ensuring all entry points to an FFI engine have consistent boundary testing guarantees developers receive graceful, unified exceptions regardless of the engine mode used.
**Action:** Added a specific `ValueError` check (`test_expanding_invalid_feature`) during `ExpandingExtractor` initialization. Future work wrapping multiple C/Rust engines should always verify the exception boundary symmetrically across all exposed classes.
